Stability and Non-Breaking Change Requirements

This application already contains working functionality.

The objective is to improve reliability, accuracy, maintainability, and trustworthiness WITHOUT breaking existing working features.

Before making any code changes:

1. Identify all affected systems.
2. Identify all dependencies.
3. Identify all upstream and downstream consumers.
4. Determine what could break if the change is applied.
5. Document the risk level of the change.
6. Propose a safer alternative if risk is high.

⸻

Change Safety Rules

Do not restructure major systems unless there is a clear architectural reason.

Do not rename routes, services, database fields, hooks, components, utilities, API contracts, or schemas without verifying every dependency.

Do not remove existing logic simply because it appears unused.

Verify whether code is:

* Referenced dynamically
* Feature flagged
* Used by scheduled jobs
* Used by admin tooling
* Used by reporting
* Used by background services
* Used by hidden routes
* Used by future workflows

before removing it.

Regression Prevention Requirements

For every bug fixed:

Create a test that reproduces the original bug.

Verify:

* Existing functionality still works.
* Existing calculations still match expected results.
* Existing sync flows still complete successfully.
* Existing projections still generate correctly.
* Existing pages still render correctly.
* Existing user actions still work.

No bug fix is considered complete until a regression test exists.
